# 别在 body 里算东西：一次 1784ms → 3.9ms 的性能排查

> 一个自己写的 macOS 小工具，功能都对了，但每敲一个字要等近两秒。查下去发现，问题不在数据量，而在「同一份计算被重复做了多少次」。

---

## 一、功能都对，就是卡

前阵子做了个小工具 CmdBook：扫描 Mac 上装过的命令行工具，记下用法和示例，支持用中文搜。比如搜「数据恢复」，会找出 photorec、testdisk。全量扫出来 2101 个工具，每个都配了中文说明。

功能验收都过了，用起来却很难受：在搜索框里敲一个字，界面要顿一下；点一条搜索结果，也要停一停。

第一反应大概是「2101 条数据太多了吧」。但这个量级真不算大——一部短篇小说的字数都比它多。真正的问题不在数据有多少，而在**同一份计算被跑了多少遍**。

## 二、先别改代码，先让它可被测量

性能优化最容易踩的坑，是凭感觉动手：觉得这里慢，改一下，好像快了点，然后就没有然后了。

这次先加了一个 `--bench`。它模拟的不是「跑一次搜索」，而是**一次真实的界面刷新**：改一次 `query`，然后按侧栏实际会读取的次数，读 6 次结果列表、读一次计数、读一次范围状态，跑多轮取平均。同时定好预算：60 fps 下每帧 16.7 ms。

结果：

```
每次输入 / 刷新  1784 ms   （预算 16.70 ms）  FAIL
```

一帧的预算里，塞了差不多 107 帧的活。

这一步的价值不在于拿到一个难看的数字，而在于**后面的每一次改动都有裁判**。测试先失败，再动手，改完再让它通过。

## 三、把 1784 ms 拆开

继续加基准，一层层量：

| 动作 | 耗时 |
| --- | --- |
| 对 2101 个工具的用法文本逐条 `String.contains` | 135 ms |
| 一次全量排序 `Search.sort(all)` | 186 ms |
| `scopeExpanded` 求值一次（内部含 2 次排序） | 57 ms |
| `matches` 求值一次（3～4 次排序） | 102 ms |
| 一次界面刷新（约 6 次 `matches`，叠加多次状态更新放大） | 约 614 ms 起 |

这 2101 个工具抓下来的帮助文本，合计约 **335 万字符**。

数字摆出来之后，根因就分成了两层：一层是「单次计算太贵」，另一层是「计算次数太多」。后者更要命。

## 四、第一层：热路径上的大文本扫描

排序评分函数对每个工具做十来次判断，最后一条是「用法文本里有没有这个词」。绝大多数工具都不命中，于是**每一个工具都要把整段帮助文本从头扫到尾**。

同一批数据、同一个查询词，换几种匹配方式对比：

| 实现方式 | 耗时 |
| --- | --- |
| `String.contains`（全量） | 135 ms |
| `String.range(of: .literal)` | 28 ms |
| 只搜前 512 字符 | 34 ms |
| UTF-8 `Data.range(of:)` | **1.31 ms** |

为什么字节匹配能快两个数量级：UTF-8 是自同步编码，字节序列的子串匹配与字符串层面的子串匹配等价，不会跨字符边界产生假命中；而 Foundation 对 `Data` 的查找走的是高度优化的字节搜索，比 Swift 的字符级 Unicode 比较轻得多。

但我要坦白说：**这一条是全文最不重要的一条。**

`Data.range(of:)` 是 Foundation 的特定技巧，换个语言、换个框架就用不上；335 万字符也是这个项目独有的规模。真正可迁移的只有一句：不要在每次交互时，重新扫描一遍全量长文本。

## 五、第二层：body 不是描述，是执行体

来看修复前那段代码。它看起来完全人畜无害：

```swift
var matches: [Tool] {
    let primary = Search.sort(scopedTools, query: query)
    if scopeExpanded { return Search.sort(tools, query: query) }
    return primary
}
```

一个计算属性，读起来像在读一个变量。

问题在于，SwiftUI 的 `body` **会被反复求值**。侧栏里 `matches.count`、`visibleMatches.count`、`scopeExpanded`、`List(visibleMatches)` 各读一次，一次界面刷新大约读 6 次；而每次读 `matches`，内部要跑 1 次主排序，外加 `scopeExpanded` 的 2 次排序，命中「当前范围没结果、自动扩大到全部工具」的分支还要再 +1 次。

于是：一次按键 ≈ 18 次全量排序。

这个坑在声明式 UI 里是通用的，跟具体框架无关：

- React：在 `render` 里直接 `.filter().sort()` 一个大数组；
- Jetpack Compose：在 `Composable` 里做全量计算却没 `remember`；
- SwiftUI：在 `body` 里放计算属性、临时创建 `DateFormatter`、拼大字符串。

共同点是：**写的时候像在写「数据」，跑起来是「代码」，而且跑几次不由你决定。**

## 六、为什么「点击结果」也卡

反馈里最有用的一句，其实不是「搜索慢」，而是「点击也不流畅」。

如果只是搜索算法慢，那清空关键词之后点击应该顺畅。但点击同样卡，说明这不是搜索独有的毛病。

原因：所有状态都挂在同一个 `ObservableObject` 上。点一行 → `selectedName` 变化 → `didSet` 连带更新当前示例、参数字段、输出、状态四个 `@Published` → 整棵视图树重算 → 侧栏的 `body` 又把那 6 次全量排序跑了一遍。

**输入卡和点击卡，是同一个根因的两个症状。**

如果把它们当成两个 bug 分头优化，大概率会得到两个补丁，以及两份新的不一致。排查时先找共享路径，往往比逐个消灭症状省事得多。

## 七、改法：一次性预建，之后只读

改动只有两处。

**一，把长文本变成索引。** 加载快照时，对每个工具的可搜索字段做一次 `lowercased()`，转成 UTF-8 `Data`，存成不可变索引；查询时只做字节比较和一次结果排序。索引随快照建立、随重扫重建。

**二，让结果只算一次。** 把 `matches` / `visibleMatches` / `scopeExpanded` / `exactChineseCount` 从计算属性改成存储属性，只在 `query`、`filter`、`snapshot` 变化时重算：

```swift
@Published var query = "" { didSet { recomputeResults() } }
@Published private(set) var visibleMatches: [Tool] = []
```

顺带把排序逻辑收拢到一处：命令行 `--search` 和界面共用同一份实现，避免「命令行结果是对的、界面是另一套」这种最难查的偏差。

## 八、修复后的数字，和我付出的代价

`--bench` 从 FAIL 变成四项全 PASS：

| 指标 | 修复后 | 预算 |
| --- | --- | --- |
| 索引构建（仅启动 / 重扫各一次） | 36～53 ms | 250 ms |
| 单次索引查询（2101 个工具） | 4.0～5.6 ms | 16.7 ms |
| 输入 + 界面刷新 | **3.9～4.9 ms** | 16.7 ms |
| 点击选择结果 | **0.7～1.0 ms** | 5 ms |

那个「约 468 倍」，是**同一基准下计算耗时**的比值，不是「体感快了 468 倍」，更不是帧率实测。这句话我不想省略，因为省略了它，整篇文章就变成标题党了。

代价同样要说清楚：

- 启动时多 36～53 ms 建索引；
- 内存里多一份约 3.35 MB 的小写字节副本，典型的空间换时间；
- 每次重新扫描都要重建索引；
- 词典或快照一旦变化，必须让缓存失效，否则会搜到旧数据。

优化从来不是白拿的，只是把成本从「每次」挪到了「一次」。

## 九、我没验证到的部分

本来想用脚本模拟真实按键、测帧时间，但系统没给辅助功能权限（AppleScript 报 -1743），没做成；也没有用 Instruments 抓真机帧数据。

所以结论的边界是：**与按键同一条代码路径的无界面基准 + 界面截图核对**，不含真机帧率曲线。主观上到底顺不顺滑，最后还是得真人敲几个字才知道。

把这条写出来，比悄悄删掉它更让人放心。

## 十、能带走的三条

1. **先给性能一个可回归的数字，再改代码。** 没有基准，「优化完了」只是一种感觉；有了基准，它才是一条能守住的线。
2. **声明式 UI 的 `body` 是执行体，不是声明。** 任何 O(n) 计算都要有明确的触发时机——状态变化时算一次，而不是藏在属性读取里等别人来读。
3. **一个根因可以长出多个症状。** 当「输入卡」和「点击卡」同时出现，先找它们共享的那条路径。

这次真正让我意外的，不是某个 API 快了 100 倍，而是一个写着 `var matches` 的东西，在一个下午里被执行了几十万次。
